# Omega 개발용 정적 검토 기록

2026-10-24 이후 설계의 기준 문서는 [Omega 시스템 설계 로드맵](../omega-roadmap.md)이다. 아래 기록은 2026-10-21 소스 검토의 근거로 유지한다.

프로세스·IPC·데이터·NN·거래·GUI의 구체 계약과 구현/검증 분할은 [상세 설계 패키지](../design/README.md)에 모았다.

추가 상세 기록: [Master configuration](../omega-master-configuration.md), [데이터·거래 파이프라인 안전 설계](../omega-pipeline-safety.md), [모바일 알림·제어](../omega-mobile-control.md).

검토일: 2026-10-21. 대상은 이 작업 공간에 복사된 Eta/Omega, TEFFPSeeker, 레퍼런스 생성기다. **애플리케이션 실행, 프로젝트 모듈 import, 테스트 실행, 거래소 호출, DB 접속, GPU 실행은 하지 않았다.** 실행 코드와 설정은 수정하지 않았다.

이 기록의 목적은 기존 시스템의 의도와 독자적인 기술을 보존하면서 Omega를 재설계할 근거를 남기는 것이다. 함수가 존재하거나 구문 분석에 성공했다는 사실은 기능의 정상 동작을 보증하지 않는다. 성능, 실거래 정확성, GPU 수치 일치, 실제 DB 상태는 아직 검증하지 않았다.

- [구조와 보존할 기능·기술](capabilities-and-design.md): 현재 연결 구조, 분석·전략·차트·탐색 기술, Omega의 계층과 인터페이스 후보.
- [결함과 검증 후보](findings.md): 소스 근거, 발생 조건, 영향, 회귀 검증 연결.
- [개발 순서와 검증 계획](implementation-and-tests.md): 단계별 완료 조건, 테스트 배치, 추후 실행할 시나리오.
- [검토 범위 및 파일별 색인](review-coverage.md): 자체 소스와 외부 코드의 검토 깊이, 남은 확인 사항.
- [원본 소스 스냅샷 색인](source-index.json): 파일 해시, 함수 위치, import와 호출 구문. 이후 수정 전후 비교의 기준.

## 재설계 판단

재사용할 핵심은 지표·전략의 아이디어, 시장 데이터 복원 경험, 차트의 상대 좌표·부분 갱신, CPU 시뮬레이션과 GPU 병렬 탐색이다. 현재 모듈의 경계를 그대로 유지하면 GUI, IPC, 데이터 형식 변경이 계산과 거래까지 전파된다. Omega에서는 계산·주문·저장 계약을 먼저 고정하고, 현재 구현을 호환 어댑터로 감싼 뒤 순차적으로 교체하는 방향이 적절하다.

우선순위는 **체결 회계와 저장 내구성 → 시간·데이터·전략 의미 통일 → IPC와 프로세스 수명 → 분석·전략·모델 경계 → GUI 교체 실험 → GPU 탐색 재연결**로 잡는다. GUI를 오래 미루자는 의미는 아니다. 화면 교체 실험은 병행하되, 화면이 거래 로직과 데이터를 다시 소유하지 않도록 한다.

## 근거의 등급

- **S: 소스 확인** — 호출명, 분기, 계산식, 트랜잭션 순서 등 코드에서 확인한 사실. 재현 테스트를 실행했다는 뜻은 아니다.
- **C: 조건부 결함** — 특정 입력·응답 순서·실패가 들어오면 소스상 문제가 발생하는 경로. 해당 조건의 실제 빈도는 미확인.
- **H: 검증 후보** — 성능·타이밍·시장 규칙처럼 실행·측정 또는 요구사항 확정이 필요한 항목.
- **D: 설계 결정 후보** — Omega에서 채택 여부를 결정할 제안. 확정 기술 스택이나 검증된 성능으로 간주하지 않는다.

외부 라이브러리 전체를 직접 구현 코드와 같은 깊이로 수작업 검증한 것은 아니다. 로컬 복사본과 원격 저장소의 완전한 동일성도 확인하지 않았다. 특히 TEFFPSeeker 원격 내용은 접근에 실패했으므로 로컬 소스가 이번 판단의 기준이다.
