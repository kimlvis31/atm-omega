# 추천안 채택 결과와 개발 측 후속 작업

2026-10-24. P01–P06 추천 방향과 P07 명시 원칙을 채택한 기록이다. U49로 새 Binance 중심 코드 구현을 허용했고 다른 기관은 후속 확장 계약만 유지한다. 운영 규칙은 system-contracts, 실제 구현은 [최신 구현 상태](../implementation/README.md)를 따른다.

## 1. 이번에 확정한 마지막 저장 장애 정책

DB 실패 시 local JSON 계열 journal로 대체 기록한다. 그 파일에도 기록할 수 없으면 신규 위험 증가를 차단하고, 확인 가능한 상태/수량과 기존 local 규칙에 따라 기존 포지션 관리·위험 축소/조회/복구를 가능한 범위에서 지속하며 critical 알람을 발생시킨다. 거래소 측 보호 주문은 새로 만들지 않는다. 수동 개입으로 자동 관리가 중단된 포지션은 다시 자동 관리하지 않는다.

알람은 DB/outbox/file 기록 성공을 기다리지 않는 별도 비차단 경로를 사용한다. 저장 불가 사실을 저장 성공처럼 표시하지 않는다. 가능한 bounded RAM 관측은 비내구 상태로 표시하고 복구 시 확보한 기록/거래소 관측과 대조한다. 재시작/전원 상실 때 소실된 이력을 완전히 복원했다고 주장하지 않는다.

## 2. 추천안 채택 기록

P01–P06은 `추천한 방향으로 잡기`로 사용자 확정에 반영했다. P07은 기존 추천 문구가 정확한 cancel 행동을 정하지 않았으므로 그 부분까지 사용자 선택이었다고 소급하지 않는다. 구현 검증 출발안은 기존 제출 주문 유지·조회/대조이며 사용자 정지/정리 종료 등 명시된 동작과 구분한다.

| 항목 | 적용 범위 | 채택 방향/개발 기본안 | 상태 |
|---|---|---|---|
| P01 저장·NN·주문 경로 장애 후 재개 | 데이터 외 장애 | 원인 복구·주문/체결/잔고/기록 대조 후 수동 재개. 데이터만의 장애 자동 재개와 구분 | 사용자 채택 |
| P02 수동 개입 포지션의 재인수 | 해당 실제 포지션/연결 전략 | 자동 재인수 금지, 현재 상태/남은 주문 확인 후 명시적 재연결·warmup 검증 | 사용자 채택 |
| P03 critical 반복 알람 종료 | incident severity revision | 확인 시 소리만 중단·미해결 표시 유지, 악화/새 사건 재알림. gate 불변 | 사용자 채택 |
| P04 모바일 사용자 범위 | 1차 제품 | 본인 소유 여러 등록 기기, 계정별 scope를 확장 가능하게 설계 | 사용자 채택 |
| P05 실제 수신 원본 보관 | 선택된 수집 channel | 정규화 원본/lineage 유지, 무거운 payload 선택 capture·용량 상한. 원본을 MC로 대체하지 않음 | 사용자 채택, 수치 설계 예정 |
| P06 주식의 첫 상품 범위 | 증권사 첫 검증 | 국내 현금주식부터, 상품별 capability 확장. 기관 지원 목표 유지 | 사용자 채택 |
| P07 사용자 정지 외 장애의 미체결 진입 | 데이터/NN/저장/주문 경로 장애 | 장애별 명시/대조 원칙 채택. 개발 기본안은 이미 제출된 주문 유지·조회/대조, implicit cancel 없음 | 원칙 채택·세부는 개발안 |

P01은 신규 진입 재개 정책이다. 저장 장애 중 가능한 기존 관리와 코어 재시작 후 대조+수동 재개는 그대로 유지한다. P07의 개발 기본안은 공통 상태 계약의 표로 구체화했다. 자동 취소 override를 추가할 때는 대상/시점/실제 확인과 사용자 정지 유지 계약을 검증해야 한다. 새 사용자 질문을 초기 설계 진행의 선행조건으로 만들지 않는다.

## 3. 개발 측에서 먼저 설계·비교·측정할 항목

- 실제 process 배치/worker 수, native thread/RAM/VRAM budget, blocking wait/IPC transport·batch/lease 구현.
- GUI binding/차트/3D renderer 후보, resize·다중 차트·LOD/caching과 화면 시안. 기존 정상 전략의 상위 집계 이용 의미는 코드/fixture에서 확인하고 임의 변경이 필요할 때만 사용자 의도를 확인.
- 봉 내부 보간의 knot timing/경로 algorithm·seed 분할, CPU/GPU 수치 기준, 비용 model의 첫 후보와 독립 기대값.
- 학습 기록 주기/표본·보관일/용량 기본값, source/archive 예산. 설정 가능 요구는 이미 확정됐으므로 모든 수치 선택을 다시 사용자에게 넘기지 않고 근거와 제안값을 마련.
- core version에 맞는 외부 NN protocol·상태/shape·checkpoint·online capability, schema와 viewer의 첫 데이터/3D 화면.
- 상시 서버 비용 없는 원격 후보의 연결·권한·모바일 background/push·배포 조건 비교. 구체 제품 선택 전에 장단점/제한을 제시.
- Windows/Linux packaging·manual launch·GUI 없음/desktop agent 있음의 수명, GitHub Actions suite·release gate·dependency 관리.

이 항목들은 사용자의 새 기능 요구나 비용·운영 행동을 몰래 확대할 권한은 아니다. 근거 있는 구현안을 준비하고 필요한 제품/운영 선택만 구체적으로 확인한다. GUI launcher가 core 없이 실행되면 연결 상태와 별도 core 실행 안내를 제공하는 안 등은 시안에서 정하며 silent core 시작을 확정하지 않는다.

## 4. 사용자 선택이 아닌 외부 확인·실행 검증

| 항목 | 아직 확인하지 않은 내용 |
|---|---|
| 삼성증권 | 사용자 허용으로 1차 구현에서 제외. 특화주문·과거 제휴 사례 등 [조사 기록](samsung-api-investigation.md)은 보관하며 현행 개인 접근은 미확인. 첫 구현/릴리스 blocker 아님 |
| 다른 기관/계정 | 실제 권한·endpoint 한도·상품/모의환경 차이·reconnect/관측 계약 |
| 장치/플랫폼 | 중간급 PC의 10계정/약 100전략 workload 성능·메모리, Windows/Linux 및 Triton 지원 조합 |
| 안전·이관 | 실제 fault injection·legacy 비교·CPU/GPU parity·DB/JSON 복구·migration/restore·패키징 |

공개 문서 조사와 설계 정합성 확인은 실제 API 연결/거래·학습·시뮬레이션·장애 시험 통과와 구분한다. 다음 단계는 남은 질문을 무작정 늘리는 것이 아니라 위 계약과 구현 작업을 구체화하고, 코드 수정 허용 이후 최소 경로부터 검증하는 것이다.
